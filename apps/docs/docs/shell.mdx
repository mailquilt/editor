`<mail-quilt>` is only the editor. Around it, your app still needs somewhere to export the email, somewhere to show why an email was refused, and a way to keep the person's work. `<mail-quilt-shell>` is all of that in one element: the editor, with the Shell's own controls in the editor's top bar, and a message bar below it. The page has one header.

## What it has

On the left of the top bar, before Undo and Redo, are the heading, which names the email, and with `save-key`, whether it's saved: "Saved" once the email showing is the one saved, or "Not saved" when the browser can't save it. An email you open isn't saved until the person's next change, so until then neither shows. On the right, after the Desktop and Phone views, are More and Export:

- **Export** opens a menu of two files. **HTML file** downloads the email as `email.html`, ready to send. **JSON file** downloads it as `email.json`, the [document format](./document-format) the editor saves. With nothing in the email, Export is off, and its tooltip says to add something first.
- **More** opens a menu with **Not on this device**, how the email shows a Block or Row that isn't on the device being viewed: **Fold**, a thin strip that can still be selected, the default; **Fade**, full size and faded, with a tag; or **Hide**, not drawn, while the Rows list still marks it. With `save-key`, the browser keeps the choice for every Shell on the site. Then comes **Import JSON…**, which opens a `.json` file in place of the current email, which undo can't bring back, and with `save-key` it's saved straight away. If the editor refuses it, the message bar says why and the current email stays.

The message bar shows emails the editor refuses, exports that fail and saves that fail. When the browser can't save, its message has an Export JSON button, while JSON file is in the Export menu. Screen readers announce each message. A message stays until the person's next change, and one that the browser can't save stays until a change saves. One about an import also goes once an import works, and one about an export once either export works. The [Playground](/playground) is a Shell.

## Saving

With `save-key`, the Shell keeps the email in the browser's `localStorage` under that key:

- When the Shell opens, an email saved under the key opens instead of `value`. `value` is the email to start from when nothing is saved yet.
- Setting the starter email again doesn't replace the open email, so the person's work stays, on their first visit as on later ones. While a saved email is open and the Shell opened without a starter email, setting nothing doesn't replace it either, and nor does setting an email for the first time, which then becomes the starter email. So a React component that renders again, or gets its starter email late, can't replace the person's work. Any other `value` works as on `<mail-quilt>`: a different email opens, and setting it to nothing empties the editor. A different email you open over a saved one is saved with the person's next change, so if they reload before changing it, the saved email opens again. An import that changes the email is saved straight away.
- If the saved email can't be opened, such as one saved by a newer version of Mail Quilt, the message bar says why and `value` opens instead. The person's next change is saved over it, so its text is first copied to `<save-key>:unopened`, where nothing saves, and your app can still read it. If that already holds a different email, it goes to `<save-key>:unopened:2`, then `:3` and on, so no copy is lost. The same email opened again isn't copied twice. If the browser can't copy it there, such as when storage is full, no change is saved over it, and the message bar says the browser can't save.
- Each change is saved under the key. With the Shell open in two tabs, each saves over the other, so the last change wins. If the browser can't save, because storage is blocked or full, the message bar says so, and suggests Export JSON while that button shows.

Use a key of its own for each email and each person. Two emails under one key open as one, and on a shared browser one person's email opens for the next. Start the key with your app's name, so no other app on the same origin uses it, and add the IDs your app already has, such as `my-app:${userId}:${emailId}`. The examples above have one email and one key. Set the key before the Shell opens, as the examples do. If you change it later, the email saved under the new key opens. With nothing saved there, the current email stays and is saved under the new key from its next change. A message that the browser can't save, or that the saved email couldn't be opened, goes when the key changes, until the new key fails too. Removing the key stops the saving, and setting the starter email again still leaves the open email.

Opening the saved email doesn't fire `mq-change`, because the person hasn't changed anything. If your app keeps its own copy of the email, read `value` from the element once it has loaded, such as from the `ref` in React, rather than assuming it's the email you passed.

Without `save-key`, the Shell stores nothing. Save the email yourself from `mq-change`, as the [quick start](./quick-start) does. `mq-change` fires with or without `save-key`, so you can keep the email in the browser and on your server too.

## The Shell's API

The Shell takes `value`, `heading`, `actions` and `save-key`, and the editor's `uploadImage`, `fonts`, `mergeTags`, `starterEmails` and `socialIconsUrl` properties, which it passes on, so people can [upload images](./upload-images), pick [your web fonts](./api#web-fonts), [Merge Tags](./api#merge-tags) and [Starter emails](./api#starter-emails), and the [Social icons](./social-icons) load from your storage. It fires `mq-change` and `mq-error`, and has `exportHtml()`. In React, these are the `value`, `heading`, `actions`, `saveKey`, `uploadImage`, `fonts`, `mergeTags`, `starterEmails`, `socialIconsUrl`, `onChange` and `onError` props, with `actions` as an array of names. The [editor's API](./api#the-shell) describes each one.

## Customizing it

Set `heading` to name what's being edited, such as `heading="Welcome email"`.

Choose what the Shell offers with `actions`. An app that keeps emails on its own server may want only the HTML file, so people don't move emails around as files:

```html
<mail-quilt-shell actions="export-html"></mail-quilt-shell>
```

```tsx
<MailQuiltShell actions={["export-html"]} />
```

`export-html` and `export-json` are the Export menu's items, and `import-json` is More's. They keep their own order, whatever order you name them in. Export shows while it has an item. More always shows, as it has Not on this device too, so `actions=""` shows only More. Without `export-json`, a failed save says the browser can't save without suggesting it. If you leave out `export-html`, call `exportHtml()` from a control of your own, so people can still get the HTML.

The Shell draws its controls and messages from the same [theme tokens](./theme-tokens) as the editor. Set them on `<mail-quilt-shell>`, and the editor inside uses them too. So does `theme`: `<mail-quilt-shell theme="dark">` gives the Shell and its editor the [dark theme](./theme-the-editor#a-dark-theme).

To restyle the Shell beyond the tokens, its frame and each piece of the header and the message bar are CSS parts. Style them from your own stylesheet with `::part()`:

| Part          | What it is                                                  |
| ------------- | ----------------------------------------------------------- |
| `frame`       | The frame, with its corners and its 1px ring.               |
| `header`      | The top bar, which is the editor's, with the Shell's in it. |
| `heading`     | The heading's text.                                         |
| `status`      | Whether the email is saved, with `save-key`.                |
| `actions`     | More and Export, on the right of the top bar.               |
| `export`      | The Export button, while it shows.                          |
| `import-json` | Import JSON in the More menu, while it shows.               |
| `export-json` | JSON file in the Export menu, while it shows.               |
| `export-html` | HTML file in the Export menu, while it shows.               |
| `messages`    | The message bar, below the top bar.                         |
| `message`     | Each message in the bar.                                    |

```css title="styles.css"
mail-quilt-shell::part(header) {
  background: #f8fafc;
}

mail-quilt-shell::part(heading) {
  font-size: 16px;
}
```

## Shell or `<mail-quilt>`?

Use the Shell when the editor is a page of its own and its top bar can be the page's controls. It gets an editor page working with a few lines, and a refused email or a failed save always reaches the person.

Use `<mail-quilt>` on its own when the editor sits inside a page your app already lays out, such as beside a form with the email's subject and recipients, or when you want buttons of your own. You can choose and restyle what the Shell adds to the top bar, but you can't add to it.
