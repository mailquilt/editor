`<mail-quilt>` is only the editor. Around it, your app still needs somewhere to export the email, somewhere to show why an email was refused, and a way to keep the person's work. `<mail-quilt-shell>` is all of that in one element: the editor, with a header above it and a message bar between them.

## What it has

The header has the heading and up to three buttons:

- **Export HTML** downloads the email as `email.html`, ready to send.
- **Export JSON** downloads it as `email.json`, the [document format](./document-format) the editor saves.
- **Import JSON** opens a `.json` file in place of the current email, which undo can't bring back, and with `save-key` it's saved straight away. If the editor refuses it, the message bar says why and the current email stays.

The message bar shows emails the editor refuses, exports that fail and saves that fail. Screen readers announce each message. The [Playground](/playground) is a Shell.

## Saving

With `save-key`, the Shell keeps the email in the browser's `localStorage` under that key:

- When the Shell opens, an email saved under the key opens instead of `value`. `value` is the email to start from when nothing is saved yet.
- Setting the starting email again doesn't replace the open email, so the person's work stays, on their first visit as on later ones. While a saved email is open and the Shell opened without a starting email, setting nothing doesn't replace it either, and nor does setting an email for the first time, which then becomes the starting email. So a React component that renders again, or gets its starting email late, can't replace the person's work. Any other `value` works as on `<mail-quilt>`: a different email opens, and setting it to nothing empties the editor.
- If the saved email can't be opened, such as one saved by a newer version of Mail Quilt, the message bar says why and `value` opens instead. The person's next change is saved over it, so its text is first copied to `<save-key>:unopened`, where nothing saves, and your app can still read it. If the browser can't copy it there, such as when storage is full, no change is saved over it, and the message bar says the browser can't save.
- Each change is saved under the key. With the Shell open in two tabs, each saves over the other, so the last change wins. If the browser can't save, because storage is blocked or full, the message bar says so, and suggests Export JSON while that button shows.

Use a key of its own for each email and each person. Two emails under one key open as one, and on a shared browser one person's email opens for the next. Start the key with your app's name, so no other app on the same origin uses it, and add the IDs your app already has, such as `my-app:${userId}:${emailId}`. The examples above have one email and one key. Set the key before the Shell opens, as the examples do. If you change it later, the email saved under the new key opens. With nothing saved there, the current email stays and is saved under the new key from its next change. Removing the key stops the saving, and setting the starting email again still leaves the open email.

Opening the saved email doesn't fire `mq-change`, because the person hasn't changed anything. If your app keeps its own copy of the email, read `value` from the element once it has loaded, such as from the `ref` in React, rather than assuming it's the email you passed.

Without `save-key`, the Shell stores nothing. Save the email yourself from `mq-change`, as the [quick start](./quick-start) does. `mq-change` fires with or without `save-key`, so you can keep the email in the browser and on your server too.

## The Shell's API

The Shell takes `value`, `heading`, `actions` and `save-key`, fires `mq-change` and `mq-error`, and has `exportHtml()`. In React, these are the `value`, `heading`, `actions`, `saveKey`, `onChange` and `onError` props, with `actions` as an array of names. The [editor's API](./api#the-shell) describes each one.

## Customizing it

Set `heading` to name what's being edited, such as `heading="Welcome email"`.

Choose the buttons with `actions`. An app that keeps emails on its own server may want only Export HTML, so people don't move emails around as files:

```html
<mail-quilt-shell actions="export-html"></mail-quilt-shell>
```

```tsx
<MailQuiltShell actions={["export-html"]} />
```

The buttons keep their own order, whatever order you name them in, and `actions=""` shows none. Without Export JSON, a failed save says the browser can't save without suggesting it. If you leave out Export HTML, call `exportHtml()` from a control of your own, so people can still get the HTML.

The Shell draws its header and messages from the same [theme tokens](./theme-tokens) as the editor. Set them on `<mail-quilt-shell>`, and the editor inside uses them too.

To restyle the Shell beyond the tokens, each piece of the header and the message bar is a CSS part. Style it from your own stylesheet with `::part()`:

| Part          | What it is                                       |
| ------------- | ------------------------------------------------ |
| `header`      | The bar above the editor.                        |
| `heading`     | The heading's text.                              |
| `actions`     | The group of buttons on the right of the header. |
| `import-json` | The Import JSON button, while it shows.          |
| `export-json` | The Export JSON button, while it shows.          |
| `export-html` | The Export HTML button, while it shows.          |
| `messages`    | The message bar, below the header.               |
| `message`     | Each message in the bar.                         |

```css title="styles.css"
mail-quilt-shell::part(header) {
  background: #f8fafc;
}

mail-quilt-shell::part(heading) {
  font-size: 16px;
}
```

## Shell or `<mail-quilt>`?

Use the Shell when the editor is a page of its own and its header can be the page's controls. It gets an editor page working with a few lines, and a refused email or a failed save always reaches the person.

Use `<mail-quilt>` on its own when the editor sits inside a page your app already lays out, such as beside a form with the email's subject and recipients, or when you want buttons of your own in the header. You can choose and restyle the Shell's buttons, but you can't add to them.
