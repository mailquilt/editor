The editor's `exportHtml()` makes an email's HTML in the browser. `@mailquilt/renderer` makes it on your server, from the JSON document your app saved. It's the renderer the editor itself uses, and it needs no DOM. It runs in Node 22 or later.

```package-install
npm install @mailquilt/renderer
```

## Render an email

`renderEmail()` takes the document and returns a promise of its HTML:

<include meta='title="render.js"'>./_code/render.js</include>

The HTML is ready to send. Merge Tags such as `{{first_name}}` are in it as they were typed, so the service that sends your email can fill them in. An `&`, `<` or `>` inside a tag is escaped, and a `"` too in a link or image URL or alt text, as [Merge Tags](./document-format#merge-tags) explains, so keep tags to names.

[MJML](https://mjml.io), the library that writes the HTML, loads the first time you call `renderEmail()`. A server that never renders an email never loads it.

In Node 26, and any version with Web Storage on by default, that first call prints a warning once: `ExperimentalWarning: localStorage is not available because --localstorage-file was not provided.` MJML looks for a setting in `localStorage` as it loads, and stores nothing, so the warning is harmless. If your server doesn't use `localStorage` itself, you can hide it by starting Node with `--no-webstorage`, such as with `NODE_OPTIONS=--no-webstorage`.

## Social icons

A Social Block's icons are images, which an email loads from jsDelivr at the renderer's exact version, so sent emails load them from a third party for as long as they're opened. To serve them from your own storage instead, copy the renderer's `icons` folder there and give its URL as `socialIconsUrl`:

```js
const html = await renderEmail(email, {
  socialIconsUrl: "https://cdn.example.com/mail-icons/",
});
```

[Social icons](./social-icons) says why they load this way, and what to set in the editor so the canvas shows the same icons.

## Check an email before you send

`checkEmail()` lists what would go wrong for an email's readers, such as an Image with no alt text or a Button with no link. These are its Problems. Your server can stop a send that has any, or send anyway: a Problem never stops `renderEmail()`.

```js
import { checkEmail } from "@mailquilt/renderer";

const problems = await checkEmail(email, {
  mergeTags: [
    { name: "first_name" },
    { name: "unsubscribe_url", unsubscribe: true },
  ],
});
for (const { blockId, code, message } of problems) {
  console.log(code, blockId ?? "the email", message);
}
```

It takes the same document `renderEmail()` does, refuses the same emails, and renders the email to measure its HTML, with `socialIconsUrl` if you give one. Pass `mergeTags`, the list you give the editor, to check each tag's name, read without the spaces around it, so `{{ first_name }}` is `first_name`, and mark your unsubscribe tag to check that the email links to it. Without the list, neither rule runs.

The promise gives an array of Problems in the email's order: its settings first, then each Block, then the email as a whole. Each Problem has:

- `code`, one of the codes below, which stays the same in later versions.
- `message`, what's wrong and why it matters, in English, for your logs or your team. It isn't written for your customers, and its words can change.
- `rowId`, `columnId` and `blockId`, for a Problem in a Block.
- `field`, the setting that fixes it, such as `alt` on an Image, or `preheader` in the email's settings. A Problem about the email as a whole has none.
- `mergeTag`, for `unknown-merge-tag`, the tag's name, which goes between the braces.

| Code | What it means | `field` |
| --- | --- | --- |
| `empty-preheader` | The email has no preheader, or only spaces, so inboxes show its first words after the subject. | `preheader` |
| `no-language` | The email has no language, or an empty one, so screen readers may read it in the wrong voice. | `language` |
| `image-without-src` | An Image has no image, so it's left out of the email. | `src` |
| `image-without-alt` | An Image has an image but no alt text, so readers who can't see it, or whose email client blocks images, don't know what it shows. | `alt` |
| `button-without-link` | A Button has no link, so pressing it does nothing. | `href` |
| `low-text-contrast` | A Text Block's or Heading's text has less contrast with what's behind it than WCAG AA asks: 4.5:1, or 3:1 for text of 24px, or 18.67px and bold. | `color` |
| `low-link-contrast` | The links in a Text Block or Heading are in a color of their own, from Email style, with less contrast than that. A URL or email address written in the text counts, as the renderer links it. | `color` |
| `low-button-contrast` | A Button's label has less contrast than that with the Button's color. | `color` |
| `vague-link-text` | A link or Button says only "click here", "here", "read more", "learn more", "link" or "this link", in any case and with any punctuation. It checks these English phrases only. | `content` or `label` |
| `unknown-merge-tag` | A Merge Tag isn't in your `mergeTags`, such as a typo like `{{frist_name}}`. One for each tag in each place it's found. | Where the tag is, such as `content`, `href` or `preheader` |
| `html-too-large` | The HTML is over 102 KB, counted in bytes, so Gmail cuts it off and hides the rest behind a link. | None |
| `no-unsubscribe-link` | No link in the email goes to a Merge Tag you marked `unsubscribe`. A link counts when the tag is anywhere in its URL, and not when it's on an Image with no image, which is left out of the email. | None |

Contrast is read as the email shows it: a Block's own colors, or else Email style, or else the built-in look, against the Row's color, or else Email style's color behind the Rows, or else the page's. A see-through color is mixed with what's behind it. A Block with no text in it has no contrast to check.

## When the renderer refuses an email

The renderer accepts what the editor accepts. If the document is malformed, has a Block type this version doesn't know, or was saved by a newer version, the promise rejects, and the error's message says what was wrong:

```text
rows: Invalid key: Expected "rows" but received undefined
```

It never repairs an email to make it render. An email your app saved from `mq-change` always renders in the version that saved it, so a refusal usually means the JSON was changed on the way, or came from somewhere else. The [document format](./document-format) page lists what's accepted.

## Server or browser?

Export in the browser when a person is there to press a button and your app is happy to store the HTML it's given.

Render on the server when you'd rather store only the JSON, and make the HTML at the moment you send. This way an email is rendered by the version of the renderer you have installed today, and your server never trusts HTML that came from a browser.

You can do both: keep the JSON as the email, and treat any HTML as something you can make again.

## In a browser

The same build runs in a browser too. You only need it there if you're rendering without the editor, since `<mail-quilt>` already has `exportHtml()`.

Once your server has the HTML, [Send with your email service](./send-email) shows how to fill its Merge Tags for each person and send it.
